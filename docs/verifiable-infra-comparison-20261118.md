# Verification Space 与 vstack / VeriServe

2026 年 11 月 18 日。本文依据 [Towards Verifiable LLM Infra](https://haoailab.com/blogs/verifiable-llm-infra/)、vstack `16a4c035` 和 VeriServe `8345c9c9` 的源码与说明整理。本文完成的是方法和源码对照，没有复现对方的 GPU 实验或完整证明。

## 它做了什么

这项工作从 Agent 编写推理基础设施后的可靠性问题出发，提供两项成果。vstack 组织规格、抽象、模型校验、形式化验证与持续检查；VeriServe 将这些方法用于 Prefill–Decode 分离服务，以 KV 页的生命周期为中心设计执行状态和检查。文章报告在 vLLM 与 SGLang 中发现了传输、取消和缓存复用交叉发生时的问题。[文章](https://haoailab.com/blogs/verifiable-llm-infra/)

vstack 要求性质有实际问题和代码依据，模型动作能够对应源码，并用错误版本、修复版本、删除保护条件的变异以及运行轨迹检查模型是否忠实。规格文件另行锁定，防止通过弱化要求使验证通过。其当前模型评估说明分别记录轨迹符合情况、负例拒绝、历史修复覆盖及独立改动检出，强调每项指标的范围和分母。[工作流](https://github.com/hao-ai-lab/vstack/tree/16a4c0351b058130ae4a4ff6d520625c0da22b1d)、[模型评估](https://github.com/hao-ai-lab/vstack/blob/16a4c0351b058130ae4a4ff6d520625c0da22b1d/docs/model-adequacy.md)

VeriServe 的实现把“请求结束”“传输停止”和“数据对计算设备可见”分别记录。`release` 先解除请求的所有权；`_try_free` 在没有在途传输和本地计算访问时回收页。接收通知需要匹配对端、请求代次和传输身份，传输结束后还要满足可见性条件才能计算；无法取得停止证据时，页被隔离。前缀发布另外检查数据完整、所有权及在途写入。[页生命周期实现](https://github.com/hao-ai-lab/veriserve/blob/8345c9c9da1e45b4988599e488c8566130a2fc19/python/minisgl/disagg/ledger.py#L384)

证明材料的结论是设计模型在 `Sizes`、`Design` 假设下始终满足 `Safety`。当前说明明确把终止性与这一安全性定理分开，也没有声称已经证明 Python 实现对模型的细化关系。硬件完成通知的语义是证明前提之一。文章的 TPOT 数字衡量服务运行开销，不能用于表示验证时间下降。[证明范围与前提](https://github.com/hao-ai-lab/veriserve/blob/8345c9c9da1e45b4988599e488c8566130a2fc19/verification/pd-disagg/proofs/README.md)、[实现与模型的关系](https://github.com/hao-ai-lab/veriserve/blob/8345c9c9da1e45b4988599e488c8566130a2fc19/README.md#2-check-the-formal-specification-trace--proofs)

## 与当前工作的关系

双方都需要回答“系统应该保证什么”以及“抽象是否忠实于实现”。从源码提炼性质、保留配置假设、记录跨组件依赖和源码依据，已有实质重合。将这些过程组织成网页，或增加已归类测试的数量，本身不能确立新的研究贡献。

当前 Verification Space 希望形成跨功能、跨实现的验证需求模型，后续据此独立编写测试和研究剪枝。vstack 已经提供通用的验证工作流，VeriServe 则给出 KV 生命周期的具体模型、实现和证据。因此，需要比较的是我们的空间能否表达不同功能的验证对象、条件、性质、观察方法及组合关系，并能指导独立检查，而不是仅比较覆盖了多少模块。这个研究价值仍需用具体规格和实现对照建立。

三万余条上游测试继续作为需求盘点与缺口核查材料。每项测试的实际断言用于说明已有证据覆盖了什么；统一性质来自系统应当满足的语义，不由测试目录或数量决定。

## 对空间的具体检查

现有空间已经包含以下单元。这篇工作提供了进一步检查它们边界的依据，不能把对方在新版本上的问题直接记为我们固定版本中的错误。

| 现有单元 | 需要明确的条件和关系 |
| --- | --- |
| `abort.inflight_release`：在途访问完成前不复用资源 | 分别记录取消、最后一次访问、可信停止证据和重新分配；请求终止与页可复用是两个判断。 |
| `disagg.transfer_gate`：接收后继续执行 | 分开表示数据传输完成、对消费设备可见、请求身份仍有效；失败时的资源处理还依赖在途访问。 |
| `cache.lifetime`、`cache.state_invariants`：生命周期与资源计数 | 页所有者、请求代次、共享引用和在途持有者共同决定是否能够释放；安全回收与最终回收分别记录。 |
| `cache.safe_reuse`：缓存复用 | 内容匹配之外，还要核对发布时完整性、有效所有权和写入是否结束。 |
| `disagg.request_binding`：请求身份 | 区分逻辑请求、物理页及其复用代次，检查迟到消息是否会操作新的请求。 |

回读固定版本后，已修正两处表述。vLLM 的延迟释放队列允许队首未完成项推迟后面已满足条件的页回收，因此删去“其他请求的在途工作不延迟释放”的一般性要求；安全复用与回收进展分别记录。SGLang 的接收失败单测模拟失败状态并检查清理调用，现将该证据写为请求状态清理，物理资源重用另行依赖停止证据。[vLLM 释放队列](https://github.com/vllm-project/vllm/blob/76a0ccc209343971c6f4b56f6380a76202428385/vllm/v1/core/sched/scheduler.py#L3266)、[SGLang 失败清理测试](https://github.com/sgl-project/sglang/blob/49e384ce9d304648e9959666ecb8ce8cd98d0deb/test/registered/unit/disaggregation/test_decode_queue_cleanup.py#L69)

例如，请求 A 向页 p 写入 KV，A 随后取消，而远端写入尚未结束。如果 p 已分配给请求 B，A 的迟到写入可能覆盖 B 的数据。这个检查同时涉及请求终止、传输事件、页所有权和重新分配顺序。把几个环节分别归类，还不足以表达这条要求；规格需要将同一资源及其代次贯穿事件序列。

可先采用两项相互关联的规格。安全性要求“页重新分配前，旧所有者可能发起或已经在途的访问都已终止，或被可靠撤销”；进展要求“请求在声明的错误处理和调度条件下到达终止状态”。资源回收的进展还需要完成通知、公平调度或撤销机制等前提。具体系统可以等待、隔离或使用可靠撤销，统一规格应描述这些方法需要满足的条件，不要求所有框架采用同一套状态名。

## 接下来的工作

继续审查全部入口，同时为代表性性质补齐可独立实现的规格。优先用“取消时存在缓存传输”检查现有分层关系，写出输入和初始状态、操作顺序、观察事件、判定规则及环境假设，并分别回到两个固定版本核对实现与已有测试的证据。再用正确序列和违反条件的序列检查规格能否区分预期行为与错误行为。

这一步的产物是可核查的验证需求及跨组件关系。它可以在后续分别交给运行测试、状态机探索或其他验证方法实现；本阶段仍集中完成空间模型，不恢复测试选择或仿真任务。
