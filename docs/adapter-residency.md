# 适配器驻留与淘汰验证规格

适配器驻留验证接收一段加载、使用、固定、移除和切换适配器的操作序列，检查容量限制下保留了哪些适配器，以及活动槽位对应哪个适配器。它与“请求使用正确适配器权重”相连，但两项检查的观察对象不同：前者看驻留集合、被淘汰对象和槽位，后者还要看请求实际计算所用的权重及输出。

每次检查须固定注册容量、活动槽位容量、当前驻留集合、可淘汰候选、当前批次所需适配器、在途保护策略、固定状态、访问顺序和声明的淘汰策略。以容量为二的状态为例，加载 A、B 后再次使用 A，再加入 C：在 LRU 策略下预期淘汰 B；在 FIFO 策略下预期淘汰 A。策略不支持或不允许自动淘汰时，应按该实现声明的拒绝行为判定。将候选集限制为部分适配器、固定一个适配器或让全部槽位不可淘汰，再检查选择结果、拒绝结果及操作后状态。基础模型若占槽位，其是否参与淘汰也按声明的规则检查。

独立测试应分别记录策略选择和完整管理器状态。策略层比较预期被淘汰的标识；管理器层检查注册集合、活动槽位、固定对象和拒绝后的状态。槽位重排后，还应将相同的请求适配器 ID 再次绑定，检查每个 token 的槽位索引是否更新；最终权重与输出的对应关系交由模型计算检查完成。这样可区分“选对淘汰对象”“槽位更新正确”和“请求最终用了正确权重”三项结论。

SGLang 的固定源码将 LRU／FIFO 策略与内存池分开实现。其策略单测覆盖访问顺序、候选子集、基础模型优先级及移除后的选择；内存池计算淘汰候选时排除当前批次所需及固定的适配器。vLLM 的管理器测试直接检查注册缓存和活动槽位在 LRU 淘汰、固定及移除后的状态；它还覆盖运行批次不变但槽位被重新分配的情况，要求再次绑定时更新 token 映射。两者都支持上述验证需求，检查入口及在途槽位的处理条件分别保留。逐项源码证据见 `experiments/semantic_space/sglang-lora-eviction-source-review.tsv` 与 `experiments/semantic_space/vllm-lora-residency-source-review.tsv`。
